# Query Language

Cardinal Data Lake uses query languages inspired by [LogQL](https://grafana.com/docs/loki/latest/query/log_queries/) (for logs) and [PromQL](https://prometheus.io/docs/prometheus/latest/querying/basics/) (for metrics). If you're familiar with either of these, you'll feel right at home — but note that **Cardinal Data Lake supports a subset of their operators and syntax**. We do not currently have full 1-to-1 compatibility with LogQL or PromQL.

---

## Log Queries (LogQL-style)

Log queries retrieve and filter log entries. A query starts with a **stream selector** and can be followed by **pipeline stages**.

### Stream Selectors

Stream selectors filter logs by label. They are enclosed in curly braces:

```logql
{label="value"}
```

#### Supported matching operators

| Operator | Description |
|----------|-------------|
| `=`      | Equals |
| `!=`     | Not equals |
| `=~`     | Regex match |
| `!~`     | Regex does not match |

#### Examples

```logql
{resource_service_name="api-server"}
```

```logql
{environment="prod", resource_service_name=~"api-.*"}
```

```logql
{environment!="dev"}
```

### Line Filter Expressions

After a stream selector, you can apply line filters to match or exclude log content:

| Operator | Description |
|----------|-------------|
| `\|=`    | Line contains string |
| `!=`     | Line does not contain string |
| `\|~`    | Line matches regex |
| `!~`     | Line does not match regex |

#### Examples

```logql
{resource_service_name="api-server"} |= "error"
```

```logql
{resource_service_name="api-server"} !~ "debug|trace"
```

```logql
{environment="prod"} |= "timeout" != "expected timeout"
```

### Label Filter Expressions

Use label filters to refine results based on parsed or indexed labels:

```logql
{resource_service_name="api-server"} | log_level="ERROR"
```

```logql
{environment="prod"} | status_code >= 500
```

## Metric Queries (PromQL-style)

Metric queries allow you to aggregate and compute over your observability data. These follow PromQL-style syntax.

### Selectors

Metric selectors use the same matching operators as log stream selectors:

```promql
http_requests_total{method="GET", status="200"}
```

```promql
cpu_usage{instance=~"web-.*"}
```

### Common Aggregation Operators

| Operator | Description |
|----------|-------------|
| `sum`    | Sum across series |
| `avg`    | Average across series |
| `min`    | Minimum value |
| `max`    | Maximum value |
| `count`  | Count of series |
| `rate`   | Per-second average rate of increase |

On a histogram metric, `sum` and `rate` do not return request counts or rates. See [Histograms](#histograms).

#### Examples

```promql
sum(rate(http_requests_total{environment="prod"}[5m]))
```

```promql
avg by (service) (cpu_usage)
```

### Range Vectors

Range vectors select a range of samples back from the current instant. Durations are specified in square brackets:

| Unit | Meaning |
|------|---------|
| `s`  | Seconds |
| `m`  | Minutes |
| `h`  | Hours |
| `d`  | Days |

```promql
rate(http_requests_total[5m])
```

### Binary Operators

| Operator | Description |
|----------|-------------|
| `+`      | Addition |
| `-`      | Subtraction |
| `*`      | Multiplication |
| `/`      | Division |
| `>`      | Greater than |
| `<`      | Less than |
| `>=`     | Greater than or equal |
| `<=`     | Less than or equal |
| `==`     | Equal |
| `!=`     | Not equal |

## Histograms

An OpenTelemetry histogram is stored under the metric's own name, with the whole distribution in each sample. It has no `_bucket`, `_count` or `_sum` series and no `le` label. Query it by its name and turn it into a number with a histogram function. The one exception is a classic Prometheus histogram sent over remote write; see [Classic Prometheus histograms](#classic-prometheus-histograms).

The examples below use a latency histogram named `http_server_request_duration`. Replace it with your metric's name, and `service_name` with the labels you want to group by.

### Recommended queries

Requests per second:

```promql
histogram_count(sum by (service_name) (rate(http_server_request_duration[5m])))
```

Mean latency:

```promql
histogram_avg(sum by (service_name) (rate(http_server_request_duration[5m])))
```

p95 latency:

```promql
histogram_quantile(0.95, sum by (service_name) (rate(http_server_request_duration[5m])))
```

Total of the observed values per second (for a latency histogram in seconds, seconds of latency per second):

```promql
histogram_sum(sum by (service_name) (rate(http_server_request_duration[5m])))
```

Share of requests that took 0.3 or less, in the histogram's unit:

```promql
histogram_fraction(-Inf, 0.3, sum by (service_name) (rate(http_server_request_duration[5m])))
```

Requests per second that took 0.3 or less:

```promql
histogram_fraction(-Inf, 0.3, sum by (service_name) (rate(http_server_request_duration[5m])))
  * histogram_count(sum by (service_name) (rate(http_server_request_duration[5m])))
```

Use `sum` to combine histogram series before applying a histogram function. Do not read a histogram with `max`, `min` or `avg`: over a cumulative histogram, `max` and `min` return nothing, as in Prometheus. For the mean, use `histogram_avg`. For the slow end of the distribution, use a high quantile such as `histogram_quantile(0.99, ...)`.

### What a histogram returns without a histogram function

A bare selector, `sum` or `rate` over a histogram does not give a request count or rate. What it returns depends on the histogram's temporality:

| Query | Cumulative histogram | Delta histogram |
|-------|----------------------|-----------------|
| `http_server_request_duration` | Each series' latest cumulative histogram: every observation since the series started | Each series' mean observed value (sum of observed values divided by their count) |
| `sum(http_server_request_duration)` | The series' latest cumulative histograms, added together | The sum of the observed values (for a latency histogram, total latency) |
| `rate(http_server_request_duration[5m])` | A histogram of the per-second increase over the window | The sum of the observed values in the window divided by the window length in seconds |

A histogram result is not a number. To chart it or compare it with a threshold, wrap it in a histogram function. An alert rule such as `sum(rate(http_server_request_duration[5m])) > 1` over a cumulative histogram goes into an error state. Write `histogram_count(sum(rate(http_server_request_duration[5m]))) > 1` instead.

### Cumulative and delta histograms

Cardinal Data Lake stores a histogram with the temporality it arrived with. That decides how precise its percentiles are:

- **Cumulative histograms with explicit buckets** are stored exactly: bucket boundaries, per-bucket counts, count and sum. `histogram_quantile` and `histogram_fraction` interpolate linearly inside a bucket, the same way Prometheus does. This needs every series you `sum` together to have the same bucket boundaries. If the boundaries differ, the result falls back to an approximate estimate. Prometheus native histograms sent over remote write are also stored exactly.
- **Delta histograms** are stored as sketches. Each bucket's observations are recorded at a single representative value inside that bucket. `histogram_quantile` and `histogram_fraction` therefore resolve to one value per bucket, with no interpolation inside a bucket. A percentile is accurate only to the width of the bucket it falls in, and it does not move while it stays within one bucket. `histogram_sum` and `histogram_avg` use the exact sum of the observed values.
- **OpenTelemetry exponential histograms** are stored as sketches whatever their temporality, so their percentiles are approximate too.

The Cardinal agent, and the collector configurations on [OpenTelemetry Collectors](/data-lake/collectors), run the `cumulativetodelta` processor. It converts cumulative histograms to delta along with counters. Histograms collected through them are delta histograms: use the histogram functions above, and expect percentiles at bucket resolution. If you need finer percentiles, give the histogram narrower buckets around the values you care about, such as your latency objective.

To see which temporality a histogram has:

```promql
count by (temporality) (http_server_request_duration)
```

### Classic Prometheus histograms

A classic histogram sent over Prometheus remote write keeps its `_bucket`, `_count` and `_sum` series and its `le` label. Query it the Prometheus way, keeping `le` in the grouping:

```promql
histogram_quantile(0.95, sum by (le, service_name) (rate(http_request_duration_seconds_bucket[5m])))
```

```promql
sum by (service_name) (rate(http_request_duration_seconds_count[5m]))
```

## Supported Subset

Cardinal Data Lake implements a **subset** of the full LogQL and PromQL specifications. While we continue to expand coverage, some advanced operators and functions may not yet be available. If you encounter an unsupported expression, reach out to our team and we'll be happy to help find an alternative or prioritize support.

For the complete specification of each language, refer to the official documentation:

- [LogQL Documentation](https://grafana.com/docs/loki/latest/query/log_queries/) — Grafana Loki's query language for logs
- [PromQL Documentation](https://prometheus.io/docs/prometheus/latest/querying/basics/) — Prometheus's query language for metrics
