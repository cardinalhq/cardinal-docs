# Install with an AI Agent

Use your AI coding agent to deploy Cardinal Data Lake on Kubernetes. Give it the install instructions below and access
to your infrastructure. The agent checks your cluster, configures storage and PostgreSQL, installs Cardinal, and
verifies the deployment by querying an ingested record.

## Before you start

Have these ready:

- An AI agent that can run `kubectl`, Helm and your provider's CLI.
- Access to your Kubernetes cluster, or a cloud/VPS account where the agent can create one.
- A [Cardinal account](https://app.cardinalhq.io) for an operator-managed install, or a license file for a manual Helm POC.
- Your preferred provider and region, plus access to object storage and PostgreSQL. The agent can help provision them.

Use the [operator-managed installation](/data-lake/install) for production. Use [manual Helm](/data-lake/manual-install)
for a POC where you manage upgrades and monitoring yourself.

## Start the install

Paste this into your agent, adding your provider, region and cluster name if you know them:

```text copy
Install Cardinal Data Lake on my Kubernetes cluster.
Fetch https://docs.cardinalhq.io/data-lake/agent-install.md and follow it.
Inspect my existing infrastructure first, then prepare the deployment configuration.
Ask me to approve paid resources or public endpoints before creating them.
Verify the installation by sending a test log and querying it back.
```

If you need a cluster, tell the agent which provider to use. For example: “Create a Kubernetes cluster on OVHcloud in
my preferred region, then install Cardinal Data Lake.”

If your agent cannot fetch URLs, copy [the full install instructions below](#install-instructions) into its context.
To reuse them as a skill, save the [raw Markdown](https://docs.cardinalhq.io/data-lake/agent-install.md) as `SKILL.md`.

## Choose your deployment path

| Target | Cluster and storage | Configuration |
|---|---|---|
| AWS | EKS, S3 and external PostgreSQL | S3 object notifications through SQS; configure pod IAM and a default StorageClass |
| Google Cloud | GKE Standard, GCS and external PostgreSQL | GCS notifications through Pub/Sub; configure Workload Identity for Lakerunner and separate HMAC credentials for the documented collector |
| OVHcloud Managed Kubernetes | Public Cloud cluster and node pool, S3 Object Storage and external PostgreSQL | Use collector gateway HTTP notifications; configure the S3 endpoint for your region and private database access |
| OVHcloud VPS/dedicated servers or another Linux VPS host | Kubernetes such as K3s, S3-compatible storage and external PostgreSQL | Provision Kubernetes first, then use collector gateway HTTP notifications; plan durable storage and backups |

The install instructions include public provider setup guides and the values for each notification route. You can
also run Kubernetes on one provider and use an S3-compatible store on another.

For S3-compatible storage, use collector gateway notifications unless the provider documents a compatible event route.
This avoids depending on bucket notification support. The gateway sends a notification after each upload; its delivery
limits are described in the instructions below.

## Confirm the result

Ask the agent to report the release name, namespace, installed version, Secret locations and verification results.
The deployment is ready when a log sent through your collector appears in a query result. Running pods or an empty
successful query are not sufficient.

Keep the generated configuration and upgrade procedure. Before running production workloads, review capacity,
backups, retention, high availability and TLS access with your operator.
