# Self-hosted setup

Storyboards need no feature flag and no extra services. Storyboards, receipts and datasets are stored in Cardinal UI's existing Postgres, and nothing is rendered in the Cardinal UI pod. This page covers what your operator configures, starting with the usual self-hosted topology: Cardinal UI inside your VPC, reachable only from your network.

On Cardinal Cloud (`app.cardinalhq.io`) all of this is already set up; see [Use with Claude](/ui/storyboards/claude).

## Requirements

- **A Cardinal UI image that includes Open Storyboards (v1.97.18 or later)** for evidence tiers, public links, the OAuth connector and personal workspaces. Storyboards themselves need v1.97.10 or later.
- **`MAESTRO_MCP_API_KEY` on the MCP gateway sidecar as well as the Cardinal UI container.** The sidecar uses it to call back into Cardinal UI when Claude creates, previews, publishes and shares a storyboard. The `maestro` Helm chart **0.10.28 or later** sets it on both containers from one Secret. Chart **0.10.29** also adds typed, install-time-validated values for the settings on this page: `maestro.trustedProxyHops` (`MAESTRO_TRUSTED_PROXY_HOPS`), `share.host` and `share.ingress.enabled` (`SHARE_HOST`), and `mcpOAuth.enabled`, `.issuer`, `.audience`, `.asMetadataProxy` and `.selfSignup` (the `MCP_OAUTH_*` variables). Setting the variables in `maestro.env` still works; don't set both. On an older chart, add the same `MAESTRO_MCP_API_KEY` entry (the same Secret and key) to both `maestro.env` and `mcpGateway.env`; see [Connect AI clients](/ui/mcp-clients#self-hosted-prepare-your-cardinal-ui-instance).
- **`GATEWAY_AGGREGATOR_ENABLED=true` on the sidecar.** Receipts are minted on the gateway's aggregated MCP endpoint, which the plugins and the OAuth connector use. With it unset, tool calls return no `[receipt:…]` trailer and there is nothing to cite:

  ```yaml
  mcpGateway:
    env:
      - name: GATEWAY_AGGREGATOR_ENABLED
        value: "true"
  ```

- **`MAESTRO_BASE_URL`** (recommended, and required for the OAuth connector and for public links without `SHARE_HOST`). With it set, the `view_url` Claude hands you is an absolute link. Without it, Claude returns an app-relative path such as `/storyboards/sb_…?org=…`; open it on your Cardinal UI host. See [Environment variables](/ui/install/environment#public-url).

Cardinal Data Lake is optional. An org with no integrations still gets the `storyboard__*` tools.

## Connect Claude inside your VPC

Inside a private network, connect Claude Code with one of these. Neither needs anything from your identity provider beyond what Cardinal UI already uses.

- **The Cardinal plugin**, `/cardinal:connect --host https://ui.example.internal`. Each user approves in the browser and gets their own key. Users must connect: until they do, the plugin's `cardinal` server points at Cardinal Cloud. See [Install: Claude Code plugin](/ui/agent-outcomes/install-claude-plugin). If your org has no Cardinal Data Lake, or `MAESTRO_INGEST_ENDPOINT` is unset, connect still sets up the MCP tools and says telemetry is unavailable.
- **The shared API key**, registered on Cardinal's aggregated endpoint. Name the server `cardinal`, so the plugins' capture hooks recognize its results as already witnessed:

  ```bash
  claude mcp add --transport http --scope user cardinal \
    "$CARDINAL_MCP_HOST/api/orgs/$CARDINAL_ORG_ID/mcp" \
    --header "X-CardinalHQ-API-Key: $CARDINAL_MCP_API_KEY"
  ```

  The key gates every org on the installation; treat it like an admin token (see [Lock it down](/ui/mcp-clients#3-lock-it-down)).

claude.ai and Claude Desktop connectors are reached from Anthropic's cloud, not from your laptop, so they can only connect to a Cardinal UI that is reachable from the internet. For an in-VPC Cardinal UI, use Claude Code.

## The OAuth connector (optional)

The OAuth connector is the org-less endpoint `<MAESTRO_BASE_URL>/mcp`. Clients discover how to sign in from it, and users sign in with your identity provider instead of holding a key. It is **off** by default.

It needs an identity provider that can hand an MCP client a client id, one of:

- **Dynamic client registration (DCR).** The client registers itself. Keycloak supports it; restrict it with a client-registration policy to public PKCE clients whose redirect URIs are on an allowlist.
- **A pre-registered client.** You create one public OAuth client with PKCE for the MCP clients, and users enter its client id when they add the connector.

**The Dex bundled with the chart has no DCR.** With it, or any provider that supports neither option, leave the connector off and use the plugin or the API key above.

### Turn it on

Set on the Cardinal UI container (`maestro.env`):

| Variable | Value |
| --- | --- |
| `MCP_OAUTH_ENABLED` | `true` |
| `MAESTRO_BASE_URL` | Your public Cardinal UI URL. Required: the endpoint is `<its origin>/mcp`. |
| `OIDC_ISSUER_URL` | Already set for the web app. `/mcp` accepts only tokens from this issuer. |
| `MCP_OAUTH_AUDIENCE` | Optional. The `aud` a connector token carries, accepted on `/mcp` only. Default `<MAESTRO_BASE_URL origin>/mcp`. A token with your `OIDC_AUDIENCE` is accepted on `/mcp` too. |
| `MCP_OAUTH_AS_METADATA_PROXY` | Optional, `true` for issuers (such as Keycloak realms) that publish discovery only at `/.well-known/openid-configuration`: Cardinal UI then serves the OAuth authorization-server metadata itself. |
| `MCP_OAUTH_SCOPES` | Optional. Default `openid profile email`. |

Cardinal UI then serves `/.well-known/oauth-protected-resource/mcp` and answers an unauthenticated `/mcp` request with `401` and a `WWW-Authenticate: Bearer resource_metadata="…"` challenge, which is how clients find your identity provider. Check it with:

```bash
curl -i https://ui.example.com/mcp
curl https://ui.example.com/.well-known/oauth-protected-resource/mcp
```

A connector token issued for the MCP audience is accepted only on `/mcp`; it can't call the rest of Cardinal UI's API. (A token issued with `OIDC_AUDIENCE`, which `/mcp` also accepts, is a normal app token.) The API-key and plugin paths keep working.

### Add the connector with a pre-registered client

- **Claude Code:** register the client with a fixed loopback redirect URI such as `http://localhost:33418/callback`, then:

  ```bash
  claude mcp add --transport http --client-id <client id> --callback-port 33418 \
    cardinal https://ui.example.com/mcp
  ```

  Add `--client-secret` only if your provider issued the client a secret.
- **claude.ai and Claude Desktop:** add Claude's connector callback, `https://claude.ai/api/mcp/auth_callback`, to the client's redirect URIs, then enter the client id under **Advanced settings** when adding the custom connector.

### Who can connect

Existing members connect to their orgs as on Cardinal Cloud; see [Which org Claude works in](/ui/storyboards/claude#which-org-claude-works-in). A user with no membership is handled like a first sign-in to the web app: pending invitations are accepted, otherwise a personal workspace is created only if self-signup is allowed.

`MCP_OAUTH_SELF_SIGNUP=true` lets anyone with a verified email create a personal workspace through the connector, even when self-signup is off for the web app. Managed email domains still refuse. It is off by default; self-hosted installs normally leave it off.

## Public links

Public links are [off by default for team orgs](/ui/storyboards/public-links#org-policy); an organization owner turns them on in **Settings → About**. Where the links point:

| Setting | Public link URL |
| --- | --- |
| `SHARE_HOST` set, for example `share.example.com` | `https://share.example.com/s/<token>` |
| Only `MAESTRO_BASE_URL` set | `<MAESTRO_BASE_URL origin>/s/<token>` |
| Neither | Links can't be created (`share_host_not_configured`). Share storyboards inside the org with their `view_url`. |

Only people who can reach that host can open a link. With an in-VPC Cardinal UI, links on `MAESTRO_BASE_URL` open only inside your network.

**Use `SHARE_HOST`.** It is a bare `host[:port]`: no scheme, no path. Point its DNS and a TLS certificate at the Cardinal UI Service, like your main hostname. On that host Cardinal UI serves only the public viewer (`/s/*`), its read API (`/api/public/*`), the **Report this page** abuse-report POST, and static assets; everything else, including sign-in and the rest of the API, answers 404, and no cookie is ever read or set. That is what makes it safe to publish:

- A Canvas that escapes its sandbox lands on an origin that holds none of your users' sessions.
- For an in-VPC install, you can route only `SHARE_HOST` through an internet-facing ingress, so outside readers reach shared storyboards while the app stays private. Pass the original `Host` header through, and keep `MAESTRO_TRUSTED_PROXY_HOPS` right for your proxies so per-reader rate limits see real client addresses.

An invalid `SHARE_HOST` stops Cardinal UI at startup rather than serving shared pages from the app's origin. With `SHARE_HOST` set, a request for `/s/<token>` on the main host is redirected to it.

`STORYBOARD_SIGNUP_URL` sets where the viewer's **Make your own with Claude** link goes (default `https://app.cardinalhq.io`).

## Personal-workspace quotas

Personal workspaces have [daily quotas](/ui/storyboards#personal-workspaces). Team orgs are never metered. Override the defaults with positive integers:

| Variable | Default |
| --- | --- |
| `PERSONAL_WORKSPACE_MAX_PUBLISHES_PER_DAY` | `20` |
| `PERSONAL_WORKSPACE_MAX_EVIDENCE_BYTES_PER_DAY` | `52428800` (50 MiB) |
| `PERSONAL_WORKSPACE_MAX_PUBLIC_VIEWS_PER_DAY` | `5000` |
